## AutoGen
| 分层设计 | 异步优先 |
|:---:|:---:|
|auto-core 负责封装LLM交互 | 允许智能体响应时处理其他任务 |
|auto-agentchat core之上LLM接口 |  |
>实现逻辑：创建实例加入所有Agent -> 按序激活Agent -> 选中的Agent根据上下文相应 -> 回复加入历史，激活下一个智能体 -> 满足对话轮次or预设终止条件 -> 结束  

>开发流程：模型客户端配置 -> 智能体角色定义 -> 定义流程顺序（参与者顺序、终止条件、最大轮次）->启动运行

### 核心智能体组件
|  |  |
|:---:|:---:|
|AssistantAgent | 任务解决者 |
|UserProxyAgent | 发起任务和传达意图执行代码，调用工具结果反向传递给智能体 |
|工作方式 | 轮询群聊让Agent按序发言 |
>**为什么Qingwen项目不选用AutoGen**: 就是轮询发言没有一个Leader会导致多个智能体一直发散讨论，难以控制。  
AutoGen核心抽象是 ConversableAgent，智能体之间通过对话自发交互，工作流是动态、自发的，灵活性极高，但也意味着行为较难控制。当 Agent 数量增多时，对话走向可能变得难以预测，想在中间插入人工审批或规则校验会比较绕路


## CAMEL
轻架构，重提示**通过角色扮演自主协作复杂任务**，核心要素角色扮演和引导性提示，角色扮演涉及到AI用户和AI助理，**AI用户提出需求，下达指令，构思任务步骤，AI助理根据指令执行具体操作和提供解决方案**。引导性提示**注入设计、结构化的初试指令，是智能体的行动纲领，需要明确自身角色，告知写作者角色，定义共同目标，设定行为约束和沟通协议**。
>实现逻辑：场景设定 -> 智能体角色 -> 定义协作任务-> 初始化角色扮演“社会” -> 启动并运行自动化对话 -> 结束  

>开发流程：框架搭建与目标对齐 -> 核心内容生成与知识库转译 -> 迭代优化与质量保证->总结升华

### 轻架构，重提示
- 多模态能⼒：⽀持⽂本、图像、⾳频等多种模态的智能体协作
- ⼯具集成：内置了丰富的⼯具库，包括搜索、计算、代码执⾏等
- 模型适配：⽀持 OpenAI、Anthropic、Google、开源模型等多种 LLM 后端
- ⽣态联动：与 LangChain、CrewAI、AutoGen 等主流框架实现了互操作性

### 对提示词工程高度依赖
- 提示设计⻔槛：需要深⼊理解⽬标领域和 LLM 的⾏为特性
- 调试复杂性：当协作效果不佳时，很**难定位是⻆⾊定义、任务描述还是交互规则的问题**
- ⼀致性挑战：不同的 LLM 对相同提示的理解可能存在差

### 协作规模的限制(双智能体协作表现出色)
- 对话管理：缺乏像 AutoGen 那样的复杂对话路由机制
- 状态同步：没有 AgentScope 那样的分布式状态管理能⼒
- 冲突解决：当多个智能体意⻅分歧时，缺乏有效的仲裁机制

### 任务适用性边界(深度协作和创造性思维任务优秀)
- 严格流程控制：对于需要精确步骤控制的任务，LangGraph 的图结构更合适
- ⼤规模并发：AgentScope 的消息驱动架构在⾼并发场景下更有优势
- 复杂决策树：AutoGen 的群聊模式在多⽅决策场景下更加灵

## LangGraph
将智能体的执⾏流程建模为⼀种状态机，将其表示为**有向图（Directed Graph）**。图的**节点（Nodes）**代表⼀
个具体的**计算步骤（如调⽤ LLM、执⾏⼯具）**，⽽**边（Edges）**则定义了**从⼀个节点到另⼀个节点的跳转逻辑**。
⽀持循环，构建能够进⾏迭代、反思和⾃我修正的复杂智能体⼯作直观和简单。

### LangGraph基本构成要素
>- **全局态**：。整个图的执⾏过程都围绕 **⼀个共享的状态对象**进⾏。这个状态通常被定义为⼀
个 Python 的 TypedDict ，它可以包含任何你需要追踪的信息，如对话历史、中间结果、迭代次数等。**所有的节点都能读取和更新这个中心状态**
>- **节点**：每个节点都是⼀个**接收当前状态作为输⼊、并返回⼀个更新后的状态作为输出**的Python 函数。节点是**执⾏具体⼯作的单元**。
>- **边**：负责连接节点，定义⼯作流的⽅向。最简单的边是**常规边**，它指定了⼀个节点的输
出总是流向另⼀个固定的节点。⽽ LangGraph 最强⼤的功能在于**条件边（Conditional Edges）**。它**通过一个函数来判断当前状态动态决定下一步应该跳转到哪个节点**。是实现循环和复杂逻辑分⽀的关键。
